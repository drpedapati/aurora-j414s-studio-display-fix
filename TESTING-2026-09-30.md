# J414s Studio Display testing — September 30, 2026

## Current outcome

Video at 5120×2880/60 Hz works. A local exp4 kernel enabled enumeration of the
Studio Display's USB functions. **Physical brightness adjustment still does
not work according to the owner's repeated visual observations**, despite
successful USB control transfers and matching input/feature replies.

These are experiments on one J414s M2 Pro and one first-generation Studio
Display (`05ac:1114`), not a qualified fix or an upstream-endorsed result.
No suspend/resume qualification, sustained audio test, or camera capture test
has been completed. Enumeration alone is not functional qualification.

## Kernel progression

| Experiment | Result | Limitation |
| --- | --- | --- |
| exp1 | First 5K picture | Reconnect failed |
| exp2 | Three same-port reconnects and one cross-side move passed | Display's USB functions absent |
| exp3 | Cold-init path ran | Probe failed with `PCIe-C oe-fabric region is required` |
| local exp4 | PCIe tunnel and xHCI initialized; USB functions enumerated | Later reconnect failures and unresolved brightness |

exp4 runs as `7.1.12-j414s-pcie-exp4+`. Its correction limits the OE-fabric
requirement to the M1 (`t8103`) path and explicitly requires Intr2AXI for the
M2 (`t6000`) path. It retains the exp3 opt-in and verified J414s DART tunables;
it did not introduce another device-tree or m1n1 change. Full Image/modules/DTB
build and module validation passed locally. **The cumulative exp4 patch is
not yet published here; do not use the exp3 patch as if it contained that fix.**

Enumerated functions included the display's USB2/USB3 hubs, `05ac:1114`,
brightness HID, ALSA Studio Display card, UVC camera, rear VIA hub, and attached
USB peripherals. Camera/audio were recognized, not proven by capture/playback.

After a macOS handoff, two reconnect attempts on controller `f01ac0000.cio`
restored video but failed to restore USB: the PCIe log repeatedly said
`link didn't come up`. Moving to the opposite-side `b01ac0000.cio` restored
the PCIe link, xHCI, and brightness HID. This suggests controller/path state
matters, but does not prove a particular teardown bug or a permanently bad port.
Earlier successful reconnects must not be presented as comprehensive reliability.

**Never live-unbind/rebind the Thunderbolt controller as a recovery recipe.**
That previously triggered a kernel NULL-pointer oops. All tests below avoided
that operation. Working video connectors changed from `USB-3` to `USB-2`
with the port move; a connector name is not proof of USB enumeration.

## Brightness microtests and what each established

| Test | Measured result | Owner observation / interpretation |
| --- | --- | --- |
| Omarchy/asdcontrol at 50%, 10%, 100% | Raw values changed | No visible panel change |
| Independent asdbctl/HIDAPI | Fresh feature reads followed 10%→100% | No visible panel change; not merely asdcontrol's cache |
| Set 37%, unplug/replug | Fresh value remained 37%; restored 100% | Retained control state, not proof of backlight response |
| Descriptor inspection | Monitor Control collection on interface 7; report 1, 32-bit brightness 400–60000 plus 16-bit field | Expected first-generation Linux interface |
| usbmon capture | SET_REPORT `21 09 0301 0007 0007`, correct payload and successful completion; subsequent GET returned requested bytes | Requests reached the USB device; physical application unproven |
| Preserve full feature report | Extra field already zero | No visible benefit |
| Pure-white compositor surface | Captured pixels were RGB 255/255/255 | Looked gray/dim; screenshot cannot measure panel luminance |
| Direct KMS color bars, 5K then 1080p | Mode and primary-plane commits succeeded outside Hyprland | White patch looked dim at both; not solely compositor or 5K-specific |
| 10%→100% while direct 1080p pattern active | Fresh reads followed commands | No visible change with compositor bypassed |
| Temporarily hold display USB runtime power `on` | Runtime remained active during writes; restored original `auto` | Repeated longer tests still showed no visible change |
| Reference presets via vendor HID interface 6 | Enumerated nine presets; active index 0, Apple Display (P3-600 nits) | Not obviously in a brightness-locked calibrated preset |
| Brief HDTV preset then return to Apple Display | Preset indices confirmed after USB re-enumeration; returned to 100% | Visible switching, but no brightness fix |
| Ambient sensor, correctly scaled | About 128.9 lux; valid temperature/chromaticity data | Sensor responds; does not establish automatic control is active |
| Passive usbmon observation | No brightness writes; final deliberate read appeared in capture and returned 100% | No overriding host brightness writer observed during that interval |
| Input-report buffer sizes | 5-byte request stalled; 7/64/100-byte requests returned 7 bytes, brightness 60000 | Earlier 5-byte stall was a receive-size quirk, not proof that input reports were unsupported |
| Nonzero 16-bit field, value 1000, with 10%→100% | Writes succeeded; feature and input returned requested brightness with extra field zero | Repeated test showed no visible benefit; Apple field semantics remain unverified |

Tests restored original brightness/report, runtime-power policy, reference
preset, and desktop session where applicable. No out-of-range brightness values,
undecoded calibration writes, USB configuration switch, or display mains power
cycle was performed.

### Test-harness corrections (important for interpreting results)

- The first white-surface target used the old `USB-3` connector name after the
  port move; it was corrected to `USB-2`. Only the corrected capture verified
  the Studio Display's white pixels.
- The initial direct KMS command supplied a mode but no plane. This libdrm
  atomic-mode test requires both and exited without holding a pattern. The
  owner's blank-screen report from that attempt is **inconclusive**.
- libdrm's `black-white` pattern alternates every pixel, so it can look gray
  at 5K. It is **not** large black/white blocks and is not evidence of dimness.
  Subsequent comparisons used SMPTE bars with a solid white patch.
- Preset changes temporarily stalled HID operations and re-enumerated USB.
  The corrected harness reopened the current device and waited between changes.
  Fresh checks verified restoration; one refresh returned approximately 24%
  before 100% was restored. That does not by itself identify the brightness bug.

## Same physical display on working macOS

Read-only SSH inspection of the owner's M3 Max (`macbook14`) over NetBird
confirmed the exact same USB serial as in the Linux evidence. No network
addresses, credentials, or private host logs are published here.

| Property | Linux exp4 | macOS 15.8 (24H20) on M3 Max |
| --- | --- | --- |
| Display | Same first-generation `05ac:1114` | Same first-generation `05ac:1114` |
| USB configuration | 1 | Current and preferred configuration 3 |
| Brightness feature report at 100% | `01 60 ea 00 00 00 00` | Exactly the same seven bytes |
| Brightness input report at 100% | Same seven bytes with sufficiently large buffer | Exactly the same seven bytes |
| Visible brightness | Owner reports dim and unresponsive | Owner confirms normal brightness |
| Automatic brightness | No overriding writes observed in passive interval | Reported disabled |

macOS reports display firmware 16.4 (20E246). A separate M5 Max was also
reachable but had a newer Studio Display XDR (`05ac:1116`) attached; it is
**not** the matched-hardware baseline. It also used USB configuration 3.

The original display's macOS reports were read with IOHIDManager/IOHIDDevice,
matching VID/PID and Monitor Control usage page 0x80 / usage 1, without changing
brightness. Both feature and input GETs succeeded and returned seven bytes.

**Configuration 1 versus 3 is a concrete difference, not a proven cause.**
Configuration 1 normally works for other Linux users. The next proposed test
is to inspect all configuration-3 interfaces and plan a reversible switch on
Linux, including changed HID interface numbering and potential camera/audio
disconnection. That test has **not happened**. Do not blindly reuse interface 7
after switching configurations or infer a fix from enumeration/readback alone.

## Research sources and limits

- [asdbctl](https://github.com/juliuszint/asdbctl): Linux configuration 1 versus
  macOS configuration/interface numbering; standard seven-byte feature writes.
  Tested local source was commit `4f0e081cd12ff511c1eb5e36306e0a346f633f8a`.
- [Original studio-brightness code](https://github.com/sfjohnson/studio-brightness/blob/main/src/hid.cpp):
  large input-report buffer and read-modify-write feature control; prompted the
  successful input-buffer-size microtest.
- [StudioBrightness++ HID map](https://github.com/LitteRabbit-37/Studio-Brightness-PlusPlus/blob/main/docs/hid-map.md):
  separate reference-preset surface, calibrated-mode brightness locking, and
  milli-lux scaling. The ambient scaling warning did not establish our cause.
- [Apple reference-mode documentation](https://support.apple.com/en-ca/108321):
  presets change color/brightness characteristics and can restrict controls.
- [USB HID Usage Tables](https://www.usb.org/sites/default/files/hut1_3_0.pdf):
  PID page 0x0f usage 0x50 is Duration. Our descriptor has second units with
  exponent −3. Interpreting Apple's use as brightness transition duration was
  a hypothesis; the bounded nonzero-field test did not fix the panel.
- [Proposed HID backlight driver](https://lists.openwall.net/linux-kernel/2023/08/06/62):
  distinguishes input brightness from feature brightness. This is a historical
  patch proposal, not a claim that installing a current stock driver fixes this.

Remaining uncertainty includes display-side application of control state,
USB configuration-specific behavior, and the shared DCP/video output path.
No calibrated photometric measurement or working-macOS USB transaction capture
was obtained. Screenshots and HID replies cannot prove physical luminance.

# Studio Display brightness investigation — October 2, 2026

## Outcome

Brightness is **not fixed on the ARM machine**. The owner reports that the
ThinkPad Nano running x86 Omarchy changes this display's physical brightness
using its keyboard brightness keys. That gives us a working Linux baseline,
not just a macOS comparison.

Local ARM exp5 (`7.1.12-j414s-pcie-exp5+`) booted and enumerated tunneled USB.
Its reconnect and suspend/resume reliability are not qualified. Published
patches in this repository still stop at exp3; this report is not an exp5 release.

## What we actually captured

- On Nano, controlled Omarchy 10%, 50%, and 100% commands produced USB writes
  and matching reads; the original setting was restored. These remotely run
  commands were **not visually confirmed** by the owner.
- A temporary Linux uinput keyboard exercised the normal Hyprland brightness
  bindings. Down/up generated the expected writes and reads. It was removed
  and brightness restored; this also was not a visually confirmed test.
- An observer was armed **before** the owner unplugged/replugged Nano and
  pressed the real brightness keys. The saved snapshot contains the disconnect,
  re-enumeration, and 77 brightness SET_REPORT requests. The owner's physical
  observation of working Nano keyboard control is distinct from USB readback.
- Saved ARM traffic from September 30 contains actual brightness payloads,
  rather than just xHCI DMA pointers. ARM's earlier visual tests repeatedly
  showed no perceived brightness change despite successful writes/readbacks.

The normal Nano key path is Hyprland `XF86MonBrightnessDown/Up` →
`omarchy-brightness-display 5%-/5%+` → Apple-display helper → `asdcontrol`.
Both hosts use asdcontrol 0.6.0. A missing ARM brightness binary is not supported
by this evidence.

## Brightness USB comparison

Both hosts identify the controller as Apple `05ac:1114`, USB device revision
`0201`, configuration 1. Brightness uses interface 7 and HID feature report 1.
The SET_REPORT setup is `21 09 0301 0007 0007`; all bytes below are hexadecimal.

| Requested level | Raw value | Seven-byte payload | Captured on |
| --- | ---: | --- | --- |
| 10% | 6360 | `01 d8 18 00 00 00 00` | Nano and ARM |
| 50% | 30200 | `01 f8 75 00 00 00 00` | Nano |
| 100% | 60000 | `01 60 ea 00 00 00 00` | Nano and ARM |
| One down step from 100% | 57020 | `01 bc de 00 00 00 00` | Nano emulated key |

The captured 10% and 100% writes match byte-for-byte, with successful USB
completion and seven transferred bytes. Nano's helper requests 64 bytes for
GET_INPUT/GET_FEATURE and receives the seven-byte report. ARM tests also
successfully read the report with appropriate sizes; changing read size has
not established a physical brightness fix.

Reconnect traffic included ordinary USB configuration/interface setup,
audio/camera class requests, and HID SET_IDLE. No additional HID feature-report
unlock write was observed in the recorded control traffic. This does **not**
prove that all display initialization is identical or rule out DP-side state.
There is no captured evidence requiring an encrypted brightness protocol.

## Newly measured video difference

| Property | Working Nano | ARM saved DCP selection |
| --- | --- | --- |
| Mode | 5120×2880, 60 Hz | 5120×2880, 60 Hz |
| Reported color depth | i915 pipe bpp 18, dithering enabled | RGB depth 10 (30 bits/pixel) |
| Compression | DSC disabled; sink supports DSC | Not established |
| Other state | HBR2, four lanes; XR24 framebuffer | SDR EOTF 0, default RGB colorimetry 16 |

Nano reports DP-3 active and a connected secondary DP-4 tile without an active
CRTC. Its `output_bpc: Maximum: 12` is a capability ceiling, **not** active
12-bit output. The shared XR24 framebuffer format does not establish identical
on-wire video format.

This is a real configuration difference, **not a proven brightness cause**.
It moves video/color/stream initialization up the investigation priority list;
it does not justify declaring a smoking gun or replaying unknown USB requests.

## Revised microtest strategy

1. Preserve the working Nano key-path capture as the reference. Compare setup,
   payload, completion, and reads separately from physical brightness results.
2. On ARM, explicitly test **8-bit RGB SDR selection**, verifying the selected
   DCP mode/depth in logs. Use a lower-resolution mode if needed to reduce
   bandwidth, and establish compression state where instrumentation permits.
   Lower resolution alone was already tried and still selected 10-bit output;
   repeating only that test would not isolate the new candidate. ARM rejects
   depths below 8, so blindly copying Nano's 6-bit/dithered pipe is not a plan.
3. Hold a fixed bright test pattern and announce low/high brightness changes
   individually for owner observation. A changed slider or returned HID value
   is insufficient. Record the actual selected video state with each result.
4. If verified 8-bit SDR does not help, inspect DCP color and DP stream setup
   against the working baseline, adding focused instrumentation instead of
   speculative reset/unlock writes.

The next video-depth test has **not yet been implemented or run**. Avoid live
Thunderbolt controller unbind/rebind: an earlier attempt caused a kernel oops.

## Capture limitations and reproducibility

These are host-side usbmon requests/completions, not a physical wire analyzer
or DP AUX capture. Seven-byte brightness payloads are fully present. Text
usbmon truncates larger data payloads in these logs (a 48-byte camera request
shows only 32 data bytes), so larger initialization requests are not completely
captured. Absence claims above apply only to recorded USB control traffic.

Nano was running `7.1.10-arch1-1 x86_64`, Intel i915, and
`omarchy-dev 4.0.0.r1849.g83881e9-1`; ARM is the J414s M2 Pro experimental
kernel described above. Different architectures make executable hashes a poor
protocol comparison; actual report bytes are the useful evidence.

Raw local logs are retained for follow-up. Full enumeration/kernel logs are
not published here because they include device serials and unrelated traffic.
This report transcribes the relevant protocol bytes and measured video state.
